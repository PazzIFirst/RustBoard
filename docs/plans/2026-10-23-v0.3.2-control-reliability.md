## 1. 目标与验收

1. **#18**：控制 HTTP 请求超时后，对应 pending 在 ≤2s 内被清理；Agent 永不响应时，
   连续请求不会被历史上限永久变成 `429 too_many_pending`；晚到应答按未知 id 丢弃。
2. **#16**：证书续签等待期间的 `ControlRequest` 不再静默丢弃；Agent 返回明确的
   `busy_renewing`，Hub 在自身超时前结束请求，审计记录可解释的错误。
3. **#15**：Panel 控制请求超时严格大于 Hub 最大控制等待（60s）；Panel 最终超时返回
   `504 control_result_unknown`，前端提示“结果未知，动作可能已执行”，不自动重试。
4. **#19**：journald 输出 >256 KiB 时保留最新日志，丢弃较旧内容；返回顺序仍为旧→新，
   `truncated=true`；普通 `exec::run` 的首部截断语义不变。
5. `cargo fmt/clippy/test`、五套既有 e2e、新增 v032 e2e、`cargo audit`、CI 全绿后打
   `v0.3.2`。

## 4. 详细方案

### 4.1 #18：ControlSession pending 超时清理

**现状**：`ControlSession` 只有 `next_id`/`pending`/`max_pending`。`dispatch()` 发送
`ControlRequest` 后把 `oneshot::Sender` 放进 `pending`；管理 API 的
`timeout(request_timeout_ms, reply_rx)` 超时只结束 HTTP 等待，不删除 pending。
只有 Agent 应答、发送失败或会话 Drop 才移除。

**实现**：

1. `ControlSession` 保存 `request_timeout: Duration`，构造签名改为：
   ```rust
   ControlSession::new(max_pending: usize, request_timeout: Duration)
   ```
   `handle_session` 用 `Duration::from_millis(cfg.control.request_timeout_ms.max(1))`。
2. `pending` 值改为：
   ```rust
   struct PendingControl {
       reply: ControlReply,
       deadline: Instant,
   }
   ```
   `enqueue()` 在插入时计算 `Instant::now() + request_timeout`。
3. 新增：
   ```rust
   fn expire(&mut self, now: Instant) -> usize
   ```
   - 遍历 `pending`，收集 `deadline <= now` 的 id；
   - 移除后向 `reply` 发送 `Err(ControlError::new(hub_codes::CONTROL_TIMEOUT,
     "控制请求超时"))`；
   - 返回清理数量；
   - 不增加 `unknown_responses`（这是本地超时，不是未知应答）。
4. `handle_session` 增加一个 1s 间隔定时器，在 `select!` 中：
   ```rust
   _ = control_expire.tick() => {
       let expired = control.expire(Instant::now());
       if expired > 0 { tracing::debug!(expired, "清理超时控制请求"); }
   }
   ```
   - 定时器只在会话存活期间存在；
   - 不阻塞采集/ACK；`expire` 只遍历内存表并发送 oneshot。
   - 首轮 tick 立即执行，随后 1s；pending 最长在 HTTP 超时后约 1–2s 内释放。
5. 管理 API 的 `timeout` 分支保持返回 `504 control_timeout`；它不再负责删除 pending。
6. Agent 晚到应答：`complete()` 找不到 id，`unknown_responses += 1`，只 debug 日志，
   不影响新请求；与 #18 的“未知 id”语义一致。

**为什么不是 API 直接取消**：API 不知道会话分配的 id，且 pending 表属于会话任务；
用会话内 deadline 清理更简单，也覆盖客户端断开、Hub 请求超时等所有路径。

**测试**：
- 单元：`ControlSession::new(1, 50ms)`，`enqueue` 一个 dummy command；`expire(now+60ms)`
  后 pending_len=0，receiver 收到 `control_timeout`；再发新命令不被 `too_many_pending` 拒绝。
- 晚到应答：expire 后 `complete(id)` 不 panic、unknown_responses=1、pending 不变。
- 并发：多个请求各自 deadline，`expire` 只删除已过期的，未过期仍在。
- 会话 Drop：仍有 pending 时全部收到 `agent_offline`（现有测试保持）。
- 集成（可用 fake session/command）：request_timeout=1s，Agent 不响应，连续 3 个请求
  都返回 504；pending 每轮被清空；不会出现永久 429。

### 4.2 #16：证书续签期间控制请求明确拒绝

**现状**：`renew_client_cert()` 的等待循环只处理 `CertRenewed`、`Ping`、`Problem`；
`ControlRequest` 走 `_ => {}` 丢弃。Hub 已分配 id 并等待 `ControlResponse`，只能超时。

**设计选择**：续签等待期间**不执行**控制动作，立即返回固定错误 `busy_renewing`。
理由：
- 证书续签是短暂、可重试的状态，不在证书切换窗口执行 root 级动作更安全；
- 不需要在续签循环里引入 dispatcher/control_rx 双写者，避免新的并发复杂度；
- 明确错误比静默丢弃或 Hub 超时更可解释，#16 验收允许该方案。

**实现**：

1. `common/src/control.rs`：
   - `codes` 增加 `pub const BUSY_RENEWING: &str = "busy_renewing";`
   - `ControlError::busy_renewing()` 返回 `ControlError::new(BUSY_RENEWING,
     "agent 正在续签证书，请稍后重试")`。
   - 这是已有 `Frame::ControlResponse.error.code` 字符串，不新增帧类型、不升协议版本。
2. `agent/src/main.rs` 的 `renew_client_cert()` 等待循环：
   - 新增分支：
     ```rust
     Frame::ControlRequest(request) => {
         let response = ControlResponse::failure(
             request.id,
             ControlError::busy_renewing(),
         );
         send_frame_with_config(sink, &Frame::ControlResponse(response), cfg).await?;
     }
     ```
   - 使用既有 `send_frame_with_config`，受 `send_timeout_secs` 约束；发送失败则结束
     续签会话并向上传播（连接已不可用）。
   - 不调用 `ControlDispatcher`，不执行目标动作；继续等待 `CertRenewed`。
   - CLI `renew` 走同一个 `renew_client_cert()`，行为一致。
3. `hub/src/control.rs` 的 `reject_from_agent_error()`：
   - `control_codes::BUSY_RENEWING` 映射：
     - HTTP `503 Service Unavailable`
     - code `busy_renewing`
     - message `agent 正在续签证书，请稍后重试`
     - 审计 `AUDIT_ERROR`（服务暂不可用，不是策略拒绝）
   - 不映射成 `control_timeout` 或 `control_failed`。
4. 日志只记录 id/错误码/帧类型，不记录证书或 CSR。

**测试**：
- Agent 单元：用 `futures_util::stream::iter` 构造 `ControlRequest(id=7)` + `CertRenewed`，
  用记录型 Sink 捕获发送帧；断言先发出 `ControlResponse{id:7,error.code=busy_renewing}`，
  随后证书续签成功落盘；请求不得触发 `systemd/docker/process/logs` 任何执行。
- 发送超时：记录型 Sink 永不 ready，`busy_renewing` 发送超时后 `renew_client_cert`
  返回发送超时错误，不无限等待。
- Hub 映射单元：`BUSY_RENEWING` → 503/`busy_renewing`/审计 error。
- 旧 hub 兼容：未知错误码会走既有 502 control_failed；仍不是超时，文档说明升级顺序。

### 4.3 #15：Panel 控制专用超时与结果未知

**现状**：`ProxyClient` 的 `reqwest::Client` 全局 `UPSTREAM_TIMEOUT=30s`；控制 POST
复用 `post_json()`。Hub 控制等待最大 60s（`MAX_REQUEST_TIMEOUT_MS`），因此配置
30,001–60,000ms 时 Panel 必先失败；`ProxyError::Unreachable` 被映射为
`502 hub_unreachable`，但动作可能已执行。

**实现**：

1. `panel/src/proxy.rs`：
   - 新增：
     ```rust
     /// 必须严格大于 Hub 最大控制等待（60s）+ 执行余量。
     const CONTROL_UPSTREAM_TIMEOUT: Duration = Duration::from_secs(70);
     ```
   - `ProxyError` 新增 `Timeout`（携带 detail 或 unit）。
   - 新增：
     ```rust
     async fn send_with_timeout(
         request: reqwest::RequestBuilder,
         timeout: Duration,
     ) -> Result<HubReply, ProxyError>
     ```
     - `.timeout(timeout)` 覆盖 client 的 30s；
     - 请求错误若 `err.is_timeout()` → `ProxyError::Timeout`；
     - 其他连接错误 → `Unreachable`；
     - 响应体读取仍走 `read_body_limited`。
   - `post_json_with_timeout(path, value, timeout)` 供控制使用；
     `post_json()` 固定调用 `CONTROL_UPSTREAM_TIMEOUT`。
   - `proxy_error_to_response()`：
     - `Timeout` → `504 Gateway Timeout`，code `control_result_unknown`，
       message `控制请求结果未知，动作可能已执行，请核对状态`；
     - 其它错误保持既有 502 语义。
2. `panel/src/main.rs` 的 `api_control_post` 不需要改调用形状；`post_json` 内部使用
   70s。普通 GET/PUT 仍用 client 30s。
3. `web/src/pages/AgentControl.tsx`：
   - 为 `control_result_unknown` 增加明确文案：结果未知、动作可能已执行、不要直接重试，
     先刷新 systemd/进程/容器状态；
   - 不自动重试危险动作，不把 504 显示成普通网络错误。
4. 为什么不加配置：70s 是 Hub 允许的最大 60s + 10s 余量；面板与 Hub 同一发布版本，
   固定常量即可，避免新增一个可能被配错的字段。若未来 Hub 提高上限，必须同步更新
   常量并加断言。

**测试**：
- 单元：`CONTROL_UPSTREAM_TIMEOUT > Duration::from_millis(MAX_REQUEST_TIMEOUT_MS)`。
- `ProxyClient::post_json_with_timeout` 对 100ms 延迟 mock hub 用 10ms 超时 →
  `ProxyError::Timeout`；`proxy_error_to_response` → 504/`control_result_unknown`。
- 正常 control POST 仍保留 Hub 的 504 `control_timeout` body，不被改写成 502。
- 可选的 31s 慢 mock hub 测试（标记为 e2e 或 `#[ignore]`，本机手动执行）：
  Hub 配置 60s、mock 延迟 31s，Panel 必须收到结果；不放进常规 CI 以控制时长。
- 前端单测/构建：错误码映射文案存在，不自动重试。

### 4.4 #19：journald tail 保留最新内容

**现状**：`tail_journal()` 调 `journalctl ... -n N`（默认旧→新），`exec::run` 的
`read_capped` 保留**前** 256 KiB；日志量大时丢掉最新行，`cap_output` 无法恢复。

**实现（最小改动）**：

1. `agent/src/control/logs.rs` 的 `tail_journal()` 参数增加：
   ```text
   --reverse
   ```
   输出变为新→旧；`exec::run` 的“保留前 256 KiB”此时保留的是**最新**内容。
2. 解析 stdout：
   - 按行拆分，若 `output.stdout_truncated` 且最后一行不是以 `\n` 结束，丢弃最后
     一条可能被截断的半行（它是最旧的一条）；
   - 先把行序反转回旧→新；
   - 再按现有 `max_lines` 逻辑丢弃最旧行（drain 前部），并 `truncate_line`；
   - 最后 `cap_output` 仍从最新往前保留总字节。
3. `size_bytes` 继续使用实际保留的 `output.stdout.len()`，并在字段注释写明
   “journal 为截断后保留的 stdout 字节数，不是 journalctl 原始总输出”。
4. `truncated` 为 true 表示“丢弃了较旧内容”，不表示丢最新。
5. 不改 `exec::run` / `read_capped`，避免影响 systemctl/docker 的首部截断语义；
   需要尾部语义的只有 journal。

**测试**：
- fake journalctl 检查参数包含 `--reverse`，输出 1000 行、每行约 1 KiB、新→旧；
  断言结果最后一行是 `line-1000`、顺序旧→新、总长度 ≤256 KiB、`truncated=true`。
- 输出 <256 KiB：不截断，顺序正确。
- 输出刚好在行中间截断：不返回半行，最新行仍保留。
- 多字节 UTF-8 行、CRLF、空行过滤、单行 >4096 字节保持既有边界。
- 普通 file tail、systemctl/docker exec 的首部截断测试全部保持。
