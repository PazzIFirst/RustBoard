# v0.3.4 低危安全清理方案

> 基线：`main@65ea48e`（v0.3.3 发布后）。关联：`docs/known-issues.md` 的
> **KI-26（中危）**、KI-18/19/21/24（低危），以及 v0.3.3 评审记录的
> `tls` 备份测试偶发失败。
>
> 目标：在进入 M4 告警与归档前，做一次**短周期、低风险**的管理面清理：
> 关闭未认证 401 放大、密码重置后的旧会话、Hello 元数据、数据目录/SQLite 权限、
> 多连接能力缓存陈旧，并稳定测试。**本阶段不新增告警、归档或安装器功能。**

## 0. 执行要求

1. 只实现本方案列出的 KI-26 / KI-18 / KI-19 / KI-21 / KI-24 与备份测试稳定性；
   **不顺手改 KI-22（硬链接）**，不改协议帧、数据库 schema、证书格式、控制动作白名单。
2. 管理面安全变更默认拒绝：失败认证超限必须 429 且不查库；密码重置后旧会话必须失效；
   非法 Hello 不得写库；数据目录/SQLite 必须收紧权限；旧连接能力不得覆盖新连接。
3. 每项必须有自动化测试，覆盖正常路径、边界值与错误路径；不能删除或弱化现有测试。
4. 兼容性：协议仍 v2；DB 无 schema 变更；新配置项有默认值；旧配置/旧 agent 不要求迁移。
5. 方案提交后暂停，不修改业务代码；等用户压缩上下文并给出开工指示后再创建 worktree。

## 1. 目标与验收

1. **KI-26**：未认证 401 不再无限驱动 SQLite + WARN；同一来源 IP 每分钟失败达到阈值后
   返回 429（带 `Retry-After`），超限路径不查库、不打 WARN；旧 `admin_token` 不受影响。
2. **KI-18**：`rustboard-panel reset-password` 落盘后，运行中的 Panel 在 ≤2s 内
   使所有已有会话失效；旧 Cookie 访问受保护端点（如 `/api/overview`）返回 401，
   公开的 `/api/session` 仍为 200 + `authenticated=false`，新密码可正常登录。
3. **KI-19**：Hello 的 `agent_id/name/hostname/os/arch/version/boot_id` 做长度与控制字符
   校验；非法帧返回固定 `Problem(bad_frame)` 并关闭，不写 agents/agent_control/审计。
   合法边界值不回归。
4. **KI-21**：hub 数据目录为 0700、SQLite 主库/`-wal`/`-shm` 为 0600；已有过宽权限在
   启动时收紧；in-memory/test 路径不受影响。
5. **KI-24**：同一 agent 多连接时，能力以**最新连接**为准；最新连接断开后回退到剩余
   最新连接的能力，不允许旧连接 Hello 覆盖新连接，也不留下陈旧能力。
6. 修复证书备份测试的偶发失败（同毫秒 + UUID 字典序导致刚创建的备份被清理）。
7. `cargo fmt/clippy/test`、`cargo audit`、既有 8 套 e2e、新增 `v034.sh`、CI 全绿后
   发布 `v0.3.4`。

## 3. 现状与风险

- **KI-26**：v0.3.3 起 scoped token 每次请求查库；401 分支在管理限速之前，且每次都
  `WARN`。本地渗透 32 并发 4000 次错误 token 约 1s、2.45 CPU-s、日志 +368KB。
  管理口默认回环；非回环 `admin_tls=required` 只做加密，不认证客户端。
- **KI-18**：Panel 会话是内存表；`reset-password` 只改配置文件，`reload_password_hash`
  只替换哈希，已有 Cookie 仍可使用到 TTL。
- **KI-19**：Hello 仅校验 `hostname`；`name/os/arch/version/boot_id` 可超长或含控制字符，
  进入 DB 与日志。
- **KI-21**：`SqliteStorage` 已把**新建**父目录设为 0700，但已存在的 0755 不会被收紧；
  SQLite 文件由默认 umask 创建，常见 0644；WAL/SHM 同样。
- **KI-24**：每次 Hello 无条件 `upsert_agent_control`；新连接断开后，旧连接仍在，但
  DB 保留新连接的能力，控制 API 可能按错误能力放行/拒绝。
- **备份测试**：后缀 `<毫秒>-<pid>-<uuid>`；同一毫秒内连续备份时，按字符串倒序可能把
  刚创建的备份排到后面并被 `prune` 删除，偶发失败。

## 4. 详细方案

### 4.1 KI-26：未认证失败限速

#### 配置

`HubConfig` 新增：

```toml
admin_auth_failure_limit_per_min = 60   # 0 = 关闭；默认 60，最大 600
```

- `#[serde(default)]`，旧配置不写该字段时默认 60。
- `HubConfig::validate`：`>600` 拒绝；`0` 明确表示关闭（仅调试/特殊部署）。

#### 限速器

在 hub 侧新增固定窗口失败计数（独立于现有 `AdminRateLimiter`，避免未认证请求消耗
已认证额度）：

```text
AuthFailureLimiter
- key: source IP
- window: 60s
- limit: admin_auth_failure_limit_per_min
- capacity: 4096 IP（满时清理过期项，仍满则拒绝新来源）
- methods: check(ip) -> Allowed | Limited{retry_after}
           record_failure(ip) -> first_in_window, just_limited
           clear(ip)（认证成功/旧 admin_token 命中时）
```

#### 请求顺序

`require_auth` 调整为：

1. 解析 `Authorization: Bearer`；缺失/格式错误：记一次失败，未超限 401，超限 429。
2. 先常量时间比较旧 `admin_token`；命中则 `clear(ip)`，按 `admin/Admin` 主体继续，
   **不受失败限速影响**（保留应急入口）。
3. scoped token：先查失败限速器；已超限 → **429，不查库**。
4. 未超限 → SHA-256 + 查库；成功则 `clear(ip)`；失败则 `record_failure(ip)`，
   未超限 401，达到阈值 429。
5. 429 固定 `{"error":"rate_limited"}` + `Retry-After: 1..=60`；不写审计、不回显 token。
6. WARN 只记每 IP 每窗口第一条失败与首次触发 429；其余 `debug`，避免日志刷屏。

**权衡**：同一 NAT 后若失败达到阈值，合法 scoped token 也会在窗口内被 429；旧
`admin_token` 常量时间路径仍可应急。默认阈值 60/min，窗口最长 60s；配置 0 可关闭。
这是为了避免未认证 DB/日志放大而接受的可用性权衡，写入 README/known-issues。

#### 测试

- 限速器：60 次允许、第 61 次 Limited、窗口边界、不同 IP 独立、容量上限、0 关闭。
- 中间件：错误 token 第 61 次 429 + Retry-After；401 不写审计；旧 admin_token 在
  限速后仍 200；合法 scoped token 在阈值前 200；429 响应不含 token。
- 日志：同一窗口只出现一条/少量 WARN（测试通过计数或 helper 断言）。

### 4.2 KI-18：密码重置吊销已有会话

- `SessionStore` 新增 `revoke_all() -> usize`（清空并返回数量；线程安全）。
- `SessionStore` 增加认证代际（`generation`）：登录先取代际、再读密码哈希；
  Argon2 完成后只有代际未变才创建会话。`reload_password_hash` 在密码写锁内
  更新哈希并递增代际，随后调用 `sessions.revoke_all()`；这样在途旧密码登录
  不能在 `revoke_all` 之后复活会话。
- `AppState::reload_password_hash` 在检测到哈希变化并写入新哈希后调用
  `sessions.revoke_all()`，`tracing::info!(revoked = n, ...)`。
- `reset-password` CLI 输出增加：“已有面板会话将在 ≤2s 内失效”。
- 只影响密码变化；普通配置重载（其他字段）不清会话。
- 测试：
  - 单元：创建 2 个会话 → `revoke_all` → 旧 token 全部 false；新 create 正常。
  - `reload_password_hash` 改变哈希后旧会话失效；相同哈希不清。
  - 代际：旧代际在 bump 后不能创建会话；并发重置 + 在途登录测试不得留下旧会话。
  - e2e：登录取得 Cookie → `reset-password` → ≤2s 后旧 Cookie `/api/overview` 401，
    旧密码登录 401，新密码登录 204。

### 4.3 KI-19：Hello 元数据校验

在 `handle_session` 完成证书 CN/agent_id 与 secret 校验后、任何 DB 写入前，调用：

```rust
fn validate_hello_metadata(hello: &AgentHello) -> Result<(), &'static str>;
```

长度上限（字节，按 UTF-8）：

| 字段 | 上限 | 空值 |
|---|---:|---|
| `agent_id` | 64 | 拒绝（沿用既有 `is_valid_agent_id` 规则，不因本阶段放宽） |
| `name` | 128 | 允许（沿用 hostname 回退） |
| `hostname` | 255 | 拒绝 |
| `os` | 64 | 允许 |
| `arch` | 32 | 允许 |
| `version` | 64 | 允许 |
| `boot_id` | 128 | 允许 |

- 所有字段拒绝控制字符（`char::is_control`）；`agent_id` 仍走现有 ID 规则。
- 失败：`send_frame(Problem { code: "bad_frame", message: "Hello 元数据非法" })`，
  随后关闭；不写 agents/agent_control、不写审计、不打印原始字段值。
- 现有 `hostname` 校验并入 helper，避免两套规则。
- 测试：每个字段 `max` 通过、`max+1` 拒绝、含 `\n`/`\t`/NUL 拒绝；
  非法 Hello 后 DB 无行；合法 Hello/Welcome 流程不回归。

### 4.4 KI-21：数据目录与 SQLite 权限

1. `common/fsutil.rs`：
   - 新增 `harden_dir(path, mode)`：存在且为目录时收紧权限；符号链接/非目录拒绝。
   - 新增 `ensure_private_dir(path, mode)`：先做路径安全校验，再创建目录并 `harden_dir`；
     只用于数据/证书目录，**不改 `ensure_dir` 对 `/etc` 配置父目录的既有语义**。
   - 新增 `validate_private_dir_path`：拒绝 `/`、`/tmp`、`/var/tmp`、`/etc` 等顶层共享
     目录、系统目录前缀、相对路径/`.`/`..`、sticky 位目录；非 root 运行时要求目录属于
     当前有效用户。HubConfig/AgentConfig 的 `data_dir` 在 `validate()` 阶段复用该规则。
2. `SqliteStorage`：
   - 默认 `open_with_readers` 只给**新建**父目录 0700，不收紧任意已存在父目录（父目录
     可能是 `/tmp` 等共享目录）；新增显式 `open_with_private_data_dir`，仅当
     `data_dir == DB 父目录` 时收紧已有目录。
   - 写连接迁移完成后 `harden(path, 0600)`；`-wal` / `-shm` 若存在也 `harden(0600)`。
   - 读连接打开后再次收紧 sidecar（防止 reader 首次创建）。
3. 数据目录调用点：
   - agent `data_dir` / DiskBuffer 父目录、hub 证书目录改用 `ensure_private_dir(0700)`；
     `/etc/rustboard` 等配置父目录保持原有 `ensure_dir` 行为。
   - hub 打开 DB 时若库位于 `data_dir` 下，使用 `open_with_private_data_dir`；否则不
     chmod 无关父目录（DB 文件本身仍 0600）。
4. hub 进程入口设置私有 umask：
   - `fsutil::set_private_umask()`（Unix `libc::umask(0o077)`），在 `main` 最早调用；
     这样 SQLite 新建的 WAL/SHM、临时文件默认 0600。
   - 证书显式 0644、私钥/配置显式 0600 的模式不受影响。
5. 不改变 DB schema/内容；不 chmod 用户指定的非数据目录父路径之外的东西。
6. 测试：
   - 新建 DB 文件 0600、父目录 0700；WAL/SHM 0600。
   - 预置 0644 DB + 0755 目录后打开，权限被收紧且可读写（显式私有目录路径）。
   - `/tmp`、`/var/tmp`、`/etc`、`/` 等共享/系统目录拒绝；sticky 目录拒绝；符号链接
     目录/数据库路径拒绝；默认 open 不改已存在共享父目录。
   - in-memory DB 跳过；重复打开幂等。
   - Agent 的 data_dir / DiskBuffer 父目录经 `ensure_private_dir` 后为 0700。

### 4.5 KI-24：多连接能力缓存

- `ConnectionEntry` 增加 `capabilities: Vec<String>`（注册时为空）。
- `SessionRegistry` 新增：
  - `set_capabilities(agent_id, conn_id, caps) -> Option<Vec<String>>`：记录到该连接；
    仅当它是当前最大 `conn_id` 时返回 `Some(caps)`，供调用方写 DB；旧连接返回 `None`。
  - `latest_capabilities(agent_id) -> Option<Vec<String>>`：返回最大 conn 的能力；
    无连接返回 `None`。
  - `is_latest(agent_id, conn_id) -> bool`。
- `handle_session`：
  - 注册后 `set_capabilities`；只有返回 `Some` 才 `upsert_agent_control`。
  - 旧连接晚到的 Hello 不覆盖 DB。
- `SessionCleanup::finish`：
  - 在注销当前连接后，若当前连接曾是 latest 且仍有剩余连接：读取
    `latest_capabilities`，best-effort 写入 `agent_control`；无剩余连接时保留最后能力
    作为历史（与现有“断线不清能力”语义一致）。
  - 状态 offline/revoked 的原子清理逻辑保持：仍在 `unregister_last_and_run` 的 slot 锁内。
  - 写能力失败只 warn，不影响连接清理/采集。
- 测试：
  - 旧 conn Hello（cap B）→ 新 conn Hello（cap A）→ DB=A；旧 conn 不覆盖。
  - 新 conn 断开 → DB 回退为旧 conn 的 B；控制 sender 指向旧 conn。
  - 两条连接都断开 → DB 保留 B（历史），状态 offline。
  - 注册后未 Hello（空能力）不误清空已有能力。

### 4.6 备份测试稳定性

`common/tls.rs`：

- 后缀改为 `<毫秒>-<进程内单调序号 8 位>-<pid>-<uuid>`；新增 `AtomicU64` 序号。
- `is_managed_backup` 识别 3 段（旧格式）与 4 段（新格式）。
- `prune_managed_backups` 按解析出的 `(毫秒, 序号)` 降序；旧格式序号按 0/字符串兜底，
  保证新备份不会因 UUID 字典序被删。
- 测试：
  - 同毫秒连续生成 `BACKUP_KEEP+2` 份，断言保留最近 KEEP 且最后一份仍在。
  - 旧 3 段格式仍被识别、不会被误删。
  - 可注入 `now_ms`/序号（cfg(test) helper），不依赖真实时间。

### 4.7 KI-22：不修

- 硬链接检测（`st_nlink>1`）需要日志目录写权限；拒绝会破坏部分 logrotate hardlink 部署。
- 保持 KI-22 open，v0.3.4 只在 known-issues/README 说明；不改变 `openat2` 行为。
- 可选：启动校验时对 `nlink>1` 打一次 `warn!`（仅诊断，不拒绝），不纳入验收硬要求。

### 6.2 e2e

1. 错误 token 连续请求：前 N 次 401，超限 429 + `Retry-After`；日志不刷屏；
